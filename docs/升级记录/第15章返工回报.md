## 1. 脚本：怎么钉的

按 NUM 的顶层分组钉，共 12 组，都用 `S.pinned(CH, 键名, measure, "CH15_RETIME")`（脚本里包了一层 `pin()`）：

## 5. 拿不准的地方

1. **重测分支没有真的跑过**。任务要求不重新计时，我只用取自现有 JSON 的假计时数据把 `CH15_RETIME=1` 的分支完整走了一遍（输出写到 /tmp，结构和现有 JSON 一致）。真实重测要等机器空闲时做一次才算验证。
2. **“另一次运行的对照”是写死在脚本里的抄录**。来源文件在 /tmp，脚本没法重新生成它。重测之后这一组不会自动更新，讲义里的对照也要跟着改，脚本的文件头和这一组的说明里都写了。是否接受这种做法请统筹的人定。
3. **“两位有效数字的写法”一组是为了过 audit 加的**。audit 按小数位数比较，三位数取两位有效数字（124 写成 120）会被判成找不到出处。另一个办法是让 `audit_numbers.py` 认有效数字，那是共享文件，我没动。
4. **“机器空闲时测的”我没法核实**，是照任务说明写进讲义和 JSON 的。钉住的这份 JSON 里，同一段代码 30 次计时最慢是最快的 3 倍，说明那次也不算安静。
5. **稳不稳只对照了两次运行**。两次都成立的结论我保留了，但样本只有两次。4096 这一列为什么波动特别大没有查。
6. **恰好在中间的数的舍入**：3.65 写成 3.6，3.75 写成 3.8，82.5 写成 82，58.5 写成 58，61.5 写成 62，20.5 写成 20，22.5 写成 22，12.5 写成 12。统一按 Python 对存储值的格式化结果，audit 两种写法都认。105 倍写成“100 倍左右”。
7. **“测试能抓住什么”的重跑保护**（见第 1 节）是我加的判断：这三种改法的结果本不该取决于耗时，但测试里有计时检查，不加保护的话机器卡顿时两遍运行可能不一样。
